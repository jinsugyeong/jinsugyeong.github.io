# 1. 딥러닝 모델을 ONNX, TensorRT 등의 포맷으로 변환해야 하는 이유는 무엇인가요?

겉으로 보기엔 "어차피 PyTorch로 학습했는데 그 상태로 쓰면 안 되나?" 싶었는데, 실제로 배포 단계까지 생각하면 이야기가 완전히 달라진다.

<!-- more -->

## 1. 호환성(Framework Agnostic) 확보

PyTorch에서 학습한 모델을 그대로 쓰면 PyTorch 환경에서만 돌아간다.
근데 실제 서비스 환경은 **Python도 없고, PyTorch도 설치 안 된** 경우가 대부분이다.
ONNX로 내보내면 다양한 백엔드(TensorRT, OpenVINO, ONNX Runtime 등)에서 공통 포맷으로 읽을 수 있어서 **"학습은 PyTorch, 배포는 다른 엔진"** 구조가 가능해진다.

## 2. 추론 속도 최적화

TensorRT는 NVIDIA GPU에 특화된 추론 최적화 엔진이다.
PyTorch 모델을 TensorRT로 변환하면:
- **레이어 퓨전(Layer Fusion)**: 여러 연산을 하나로 합쳐서 메모리 접근 횟수를 줄인다.
- **커널 자동 튜닝(Auto-tuning)**: GPU에 최적화된 커널을 선택한다.
- **정적 최적화(Static Optimization)**: 입력 shape이 고정되면 불필요한 연산을 아예 제거한다.

실무에서 같은 GPU에서 **PyTorch → TensorRT 변환 시 속도가 2~10배까지** 빨라지는 경우가 많다.

## 3. 정적 그래프 기반 최적화가 가능함

PyTorch는 동적 그래프 기반이라 실행 시마다 그래프를 다시 만든다.
ONNX나 TensorRT는 정적 그래프로 변환되므로:
- **레이어 합치기**: Conv → BatchNorm → ReLU를 한 번에 처리
- **Constant folding**: 학습 시 정해진 값은 미리 계산
- **Shape 추론 기반 최적화**: 입력 크기에 맞춰 최적의 메모리 레이아웃 사용
- **메모리 재배치 최적화**: 레이어 실행 순서를 바꿔 메모리 재사용 극대화

## 4. 하드웨어 친화적인 변환이 쉬움 (FP16, INT8 등)

PyTorch에서 직접 양자화를 하려면 코드를 많이 수정해야 한다.
하지만 ONNX → TensorRT 변환 과정에서 자연스럽게 **FP16, INT8 최적화**를 적용할 수 있다.

이유:
- TensorRT가 Calibration(보정) 기능을 제공해서 INT8 변환이 쉬움
- 변환 과정에서 동시에 양자화를 적용하면 **비용 절감 + 속도 향상 + 메모리 절감**이 동시에 달성된다.

## 5. 배포 환경 일관성

**"ONNX 파일 하나 → 어디서든 동일하게 돌릴 수 있음"**

PyTorch로 배포하면:
- Python 버전 차이
- PyTorch 버전 차이
- CUDA 버전 차이
- 의존성 라이브러리 버전 차이

이런 문제들이 전부 배포 시 잠재적 리스크가 된다.

ONNX나 TensorRT로 변환하면:
- **프레임워크 버전 이슈 제거**
- **의존성 단순화**
- **배포 패키지 크기 감소**

# 2. 양자화 기법인 Post-Training Quantization과 Quantization-Aware Training의 차이를 설명해보세요.

## 1. Post-Training Quantization (PTQ)

**"학습이 다 끝난 모델에 양자화를 나중에 적용하는 방식"**

### 장점
- 추가 학습 필요 없음
- 빠르고 간단함
- 기존 모델 그대로 변환 가능

### 단점
- 정밀도가 떨어질 수 있음
- 작은 모델이나 민감한 모델은 정확도 하락이 눈에 띄게 발생
- 데이터 분포를 완전히 반영하지 못함

## 2. Quantization-Aware Training (QAT)

**"학습 단계부터 양자화를 고려하고 학습하는 방식"**

Forward pass에서 **가짜 양자화(Fake Quantization)**를 끼워 넣어, INT8 환경에 적응하도록 학습한다.

### 장점
- 정확도 손실이 거의 없음
- INT8로 내려가도 성능 유지 가능
- 서비스에 가장 안정적

### 단점
- 학습을 다시 해야 함
- 학습 시간 증가
- 설정이 더 복잡함

## 핵심 차이 정리

| 구분 | PTQ | QAT |
|------|-----|-----|
| 적용 시점 | 학습 후 | 학습 중 |
| 추가 학습 | 없음 | 필요 |
| 정확도 | 감소 가능 | 거의 유지 |
| 속도 | 빠름 | 느림 |
| 실무 활용 | 빠른 실험 | 실제 서비스용 |

<br>
<details>
<summary>실습해설</summary>

<p>양자화(Quantization)는 모델의 가중치를 더 작은 비트로 표현해서 모델 크기를 줄이고 추론 속도를 높이는 기법입니다. 크게 두 가지 방식이 있습니다.</p>
<p>PTQ(Post-Training Quantization)는 이미 학습이 끝난 모델에 양자화를 사후에 적용하는 방식입니다. 추가 학습 없이 빠르게 적용할 수 있지만, 모델이 양자화에 적응하지 못해서 정확도가 떨어질 수 있습니다.</p>
<p>QAT(Quantization-Aware Training)는 학습 단계부터 양자화를 고려하고 훈련하는 방식입니다. 학습 중에 가짜 양자화를 적용해서 모델이 INT8 환경에 미리 적응하기 때문에, 정확도 손실이 거의 없습니다. 대신 학습을 다시 해야 하므로 시간이 더 걸립니다.</p>
<p>실무에서는 빠른 실험에는 PTQ를, 실제 서비스 배포에는 QAT를 사용하는 것이 일반적입니다.</p>
</details>

# 3. 양자화나 모델 경량화 후 실제 서비스에서 성능이 저하되지 않도록 하기 위해 어떤 테스트나 확인 절차가 필요할까요?

## 1. FP32 모델과 정량 성능 비교 (Accuracy Validation)

원본 모델(FP32)과 경량화 모델(INT8/FP16)의 정확도를 비교한다.

**중요 포인트**:
- 전체 평균뿐 아니라 **클래스별로도 확인** 필수
- **특정 클래스에서만 성능이 급격히 떨어지는지 체크**
- 기준: FP32 대비 **1~2% 이내 하락은 수용 가능**, **5% 이상 하락은 재작업 대상**

## 2. 실제 입력 데이터 기반 테스트 (Real-World Validation)

학습 데이터로만 평가하면 현업 데이터에서 문제가 발생한다.

**필수 확인 사항**:
- **실제 서비스 데이터**와 사용자 입력 분포와 유사한 데이터로 재테스트
- 학습 시 보지 못한 데이터에서도 안정적인지 확인
- 예: 조도, 해상도, 노이즈가 포함된 데이터에서 INT8 모델은 더 민감함

## 3. Latency / Throughput 성능 측정

**측정 항목**:
- **단일 추론 시간** (Inference Latency)
- **초당 처리량** (Throughput, QPS)
- **배치 크기 변화에 따른 성능**

**주의 사항**:
- TensorRT의 경우, **Warm-up 이후 성능**을 기준으로 측정
- **동적 shape vs 정적 shape** 차이도 확인

## 4. 메모리 사용량 및 안정성 체크

**확인 항목**:
- **GPU 메모리 사용량** 모니터링
- **장시간(수 시간~하루) 연속 추론 테스트** → 메모리 누수나 불안정성 확인
- **OOM(Out of Memory) 발생 여부**

## 5. PTQ 사용 시 Calibration 검증

PTQ의 경우, Calibration 데이터셋 선택이 매우 중요하다.

**권장 사항**:
- **최소 수백~수천 샘플, 실제 서비스 분포와 유사한 데이터** 사용
- Calibration 후 다시 **정확도 재검증**
- 클래스 불균형이 심하면 **대표성 있는 샘플 선별**

## 6. A/B 테스트 또는 Shadow 테스트

실제 서비스 환경에 바로 배포하지 않고, **A/B 테스트** 또는 **Shadow 테스트**를 먼저 수행한다.

**확인 항목**:
- 기존 모델(FP32)과 경량화 모델(INT8)의 **응답 차이**
- **에러 발생률**
- **특이 케이스에서 실패 여부**

## 요약

양자화 후에는 **정확도, 속도, 안정성**을 함께 검토해야 한다.

**실무 기준**:
1. 단순 수치 평가
2. 실제 입력 데이터
3. 장시간 안정성 테스트
4. A/B 테스트

<summary>실습해설</summary>

<p>양자화나 모델 경량화를 적용한 후에는 단순히 "잘 되겠지"라고 넘어가면 안 되고, 체계적인 검증 절차가 필요합니다.</p>
<p>먼저 원본 모델(FP32)과 경량화 모델(INT8/FP16)의 정확도를 비교합니다. 전체 평균뿐 아니라 클래스별로도 확인해야 하며, FP32 대비 1~2% 이내 하락은 수용 가능하지만 5% 이상이면 재작업이 필요합니다.</p>
<p>그 다음 실제 서비스 데이터로 테스트합니다. 학습 데이터로만 평가하면 현업에서 문제가 생길 수 있기 때문입니다. 추론 속도(Latency)와 처리량(Throughput)도 측정하고, 장시간 연속 추론 테스트로 메모리 누수나 불안정성도 확인해야 합니다.</p>
<p>마지막으로 실제 배포 전에 A/B 테스트나 Shadow 테스트를 수행해서, 기존 모델과 경량화 모델의 응답 차이와 에러 발생률을 비교하는 것이 안전합니다.</p>
</details>
