1. 모델 서빙이란 무엇이며, 왜 필요한가요? 실제 서비스 환경에서 서빙 프레임워크가 어떤 역할을 하나요?

모델 서빙(Model Serving)은 학습이 끝난 AI 모델을 실제 서비스 환경에서 외부 요청에 따라 추론 결과를 제공하는 과정 을 의미한다.

단순히 모델 파일을 불러오는 것을 넘어서, “모델을 하나의 서비스처럼 운영하는 것” 이 핵심이다.

1. 모델 서빙이 필요한 이유

모델은 학습이 끝났다고 바로 서비스에 쓸 수 있는 상태가 아니다.
실제 서비스 환경에서는 다음과 같은 요구사항이 생긴다.

  • 여러 사용자가 동시에 요청
  • 요청마다 빠른 응답 시간
  • 모델 안정성 및 장애 대응
  • 모델 버전 관리 및 교체

이걸 스크립트 수준의 코드로 처리하려고 하면 곧바로 구조가 무너진다.

그래서 모델을 서버 형태로 감싸는 ‘서빙 단계’ 가 필요해진다.

2. 모델 서빙의 핵심 역할

모델 서빙 프레임워크는 단순히 predict()를 호출하는 게 아니라,
아래 역할들을 함께 담당한다.

① 요청 처리

  • REST / gRPC 형태의 API 제공
  • 외부 서비스와 표준 방식으로 통신

② 모델 로드 및 관리

  • 서버 시작 시 모델을 한 번만 로드
  • 여러 요청에서 동일 모델 재사용
  • 모델 버전 관리 및 교체 지원

③ 동시성 및 성능 관리

  • 멀티 유저 요청 처리
  • 배치 처리, 비동기 처리 지원
  • GPU 자원 효율적 사용

3. 실제 서비스 환경에서의 서빙 프레임워크 역할

실제 서비스에서는 서빙 프레임워크가 모델과 서비스 사이의 ‘완충 지대’ 역할을 한다.

예를 들면:

  • FastAPI + 추론 로직
  • TorchServe
  • Triton Inference Server

이들은 공통적으로 다음을 제공한다.

  • 모델을 API로 감싸줌
  • 추론 속도 최적화
  • 에러 격리 및 장애 대응
  • 모니터링 포인트 제공

때문에 프론트엔드는 모델을 몰라도 되고, 모델 팀은 서비스 로직을 신경 쓸 필요가 없어진다.

4. 서빙 프레임워크가 없을 때 생기는 문제

서빙 프레임워크 없이 API 코드 안에서 직접 모델을 호출하면 다음 문제가 생긴다.

  • 요청마다 모델 로드
  • GPU 메모리 낭비
  • 동시 요청 시 응답 지연
  • 모델 교체 시 코드 대규모 수정

결국 “모델이 서비스의 발목을 잡는 구조” 가 된다.

5. 모델 서빙은 ‘운영 관점’의 기술

모델 학습은 연구(Research) 영역에 가깝고,
모델 서빙은 운영(Production) 영역에 가깝다.

  • 학습: 정확도가 중요
  • 서빙: 안정성, 속도, 확장성이 중요

그래서 실제 AI 서비스에서는 “모델 성능 + 서빙 구조” 가 함께 설계된다.

핵심 요약

  • 모델 서빙은 AI 모델을 서비스로 운영하기 위한 필수 단계다.
  • 서빙 프레임워크는 요청 처리, 성능 최적화, 안정성을 동시에 책임진다.
  • 모델이 아무리 좋아도, 서빙 구조가 없으면 실서비스에서는 쓸 수 없다.

실습해설

모델 서빙이란 학습이 끝난 AI 모델을 실제 서비스 환경에서 API 형태로 운영하는 것을 말합니다. 모델을 학습하는 것과 서비스로 운영하는 것은 완전히 다른 영역입니다.

학습 단계에서는 정확도가 중요하지만, 서빙 단계에서는 안정성, 응답 속도, 동시 사용자 처리 같은 운영 관점의 요구사항이 중요해집니다. 서빙 프레임워크 없이 API 코드 안에서 직접 모델을 호출하면, 요청마다 모델을 새로 로드하거나 GPU 메모리를 낭비하는 문제가 생깁니다.

그래서 TorchServe, Triton, FastAPI 같은 서빙 프레임워크를 사용해서 모델을 한 번만 로드하고 재사용하며, 동시 요청 처리, 모델 버전 관리, 장애 대응까지 자동화합니다. 모델 서빙은 AI 모델을 '서비스'로 만들기 위한 필수 단계라고 할 수 있습니다.

2. Streamlit, FastAPI로 구성된 시스템에 Triton 기반 추론 서버를 통합하려면 어떤 구조로 설계하는 것이 바람직하다고 생각하나요?

Streamlit과 FastAPI로 구성된 AI 서비스에 NVIDIA Triton Inference Server 를 통합하려면,

각 컴포넌트의 역할을 명확히 분리하는 구조가 가장 바람직하다고 생각한다.

핵심은 “UI, API, 추론 엔진을 완전히 분리하는 것” 이다.

1. 전체 구조 개요

이 구조에서 Triton은
순수하게 추론만 담당하는 독립 서버로 동작한다.

2. Streamlit — UI 전용 레이어

Streamlit은 사용자 인터페이스와 입력 처리만 담당한다.

  • 텍스트/이미지 입력
  • 옵션 선택
  • 결과 시각화

중요한 점은:

  • Streamlit에서 Triton을 직접 호출하지 않음
  • 모든 요청은 FastAPI를 거쳐서 전달

Streamlit은 “보여주기 위한 서버”이지, 추론 로직이 들어갈 자리가 아니다.

3. FastAPI — 제어 및 오케스트레이션 레이어

FastAPI는 시스템의 중앙 제어 계층 역할을 한다.

담당 역할:

  • 요청 검증 및 전처리
  • 인증/권한 체크
  • 비동기 요청 처리
  • Triton 서버 호출
  • 결과 후처리

FastAPI는 Triton과

  • HTTP 또는 gRPC 방식으로 통신하며,
  • 클라이언트와 Triton 사이의 완충 지대 역할을 한다.

4. Triton Inference Server — 추론 전용 서버

Triton은 모델 서빙에 특화된 추론 엔진 이다.

Triton의 역할:

  • 모델 로딩 및 버전 관리
  • 배치 추론 자동 처리
  • GPU 자원 효율적 사용
  • FP16 / INT8 최적화 모델 실행

여기에는:

  • 비즈니스 로직 없음
  • 인증/권한 없음
  • 오직 “추론 요청 → 추론 결과 반환”만 담당

5. 통신 방식

Streamlit ↔ FastAPI:

  • REST API (HTTP)
  • Public Network

FastAPI ↔ Triton:

  • gRPC (고속 통신) 또는 HTTP
  • Private Network (외부 접근 차단)

6. 보안 설계

Triton은 외부에 직접 노출되지 않음

  • FastAPI가 게이트웨이 역할
  • Triton은 내부 네트워크에서만 접근 가능
  • 인증/권한은 FastAPI에서 처리

7. Docker 배포 구조

8. 장점 요약

역할 분리:

  • Streamlit: UI만
  • FastAPI: API 제어만
  • Triton: 추론만

확장성:

  • Triton은 수평 확장 가능 (여러 GPU 서버)
  • FastAPI는 로드밸런싱 가능

유지보수성:

  • 각 컴포넌트를 독립적으로 업데이트 가능
  • 모델 교체 시 Triton만 재시작

핵심 요약

  • Triton은 순수 추론 전용 서버로 완전히 분리
  • Streamlit → FastAPI → Triton 구조가 최적
  • FastAPI는 요청 제어, Triton은 성능 담당
  • 이 패턴은 실제 프로덕션 환경에서도 사용되는 표준 구조

실습해설

Streamlit + FastAPI 시스템에 Triton Inference Server를 통합할 때 핵심은 각 컴포넌트의 역할을 완전히 분리하는 것입니다.

Streamlit은 UI만 담당합니다. 사용자 입력을 받고 결과를 보여주되, 직접 모델을 호출하지 않고 모든 요청을 FastAPI로 전달합니다. FastAPI는 중앙 제어 역할로, 요청 검증, 인증, 전처리를 수행하고 Triton 서버를 호출합니다. Triton은 순수하게 추론만 담당하는 독립 서버로, 모델 로딩, 배치 추론, GPU 자원 관리를 최적화합니다.

통신 방식은 Streamlit과 FastAPI 사이는 REST API, FastAPI와 Triton 사이는 gRPC(고속 통신)를 사용합니다. 보안상 Triton은 외부에 직접 노출하지 않고, FastAPI가 게이트웨이 역할을 하며 내부 네트워크에서만 Triton에 접근할 수 있도록 설계합니다.
