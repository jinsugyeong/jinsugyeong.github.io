# 1. LangChain을 사용해 RAG 시스템을 구축할 때 어떤 주요 구성 요소들이 필요하고, 각각 어떤 역할을 하나요?

## 핵심 구성 요소 및 역할

1. 문서 소스(Document Sources)
   - 역할: 원천 콘텐츠 제공(웹 페이지, PDF, 데이터베이스, 내부 문서, 로그 등).
   - 유의사항: 메타데이터(문서 ID, 날짜, 출처 등)를 함께 보존하면 출처 표기·갱신 추적에 유리하다.

<!-- more -->

2. 전처리 및 청킹(Text Preprocessing & Chunking)
   - 긴 문서를 의미 단위로 분할해 검색 단위를 생성
   - 청크 크기와 겹침 비율이 검색·생성 품질에 큰 영향(500~2,000 토큰 범위 실험 권장)

3. 임베딩(Embeddings) 모듈
   - 텍스트 청크를 고차원 벡터로 변환해 의미 기반 유사도 검색에 사용
   - SentenceTransformers, OpenAI Embeddings, Cohere, S-BERT 등 선택 가능

4. 벡터 저장소/인덱스(Vector Store / Index)
   - 임베딩 벡터를 저장하고 빠른 근사 최근접이웃(ANN) 검색 제공
   - FAISS, Annoy, Milvus, Pinecone, Chroma 등 대표 솔루션

5. 검색기(Retriever)와 랭커(Reranker)
   - 쿼리 임베딩과 벡터 스토어를 이용해 후보 문서(청크) 반환
   - 벡터 기반 단독, BM25 같은 sparse + vector 하이브리드, 파이프라인 권장

6. LLM(Generator / Reader)
   - 검색된 문서(컨텍스트)를 입력으로 받아 응답 생성 또는 정답 추출
   - 생성 모델은 반드시 근거(출처)와 함께 응답하도록 프롬프트 템플릿 설계

7. 프롬프트 템플릿/콘텍스트 조합기
   - 검색 결과와 사용자 쿼리를 논리적으로 결합하여 LLM에 전달
   - 토큰 예산 내에서 핵심 정보만 넣도록 정리·요약 단계 고려

8. 장고(증거집합) 요약기 또는 컨텍스트 필터러(Refiner)
   - 많은 후보 청크를 압축해 핵심 문장만 추출
   - 중복·모순 문장을 걸러 LLM 입력을 최적화

9. 검증기(Verifier) / Fact-check 모듈
   - 생성 결과의 사실성 검증 또는 근거-일치성 점검
   - 민감 도메인에서는 반드시 후검증 + 사람 검토 병행

10. 운용 인프라(Orchestration & Serving)
    - 전체 파이프라인 연결·스케줄링, 요청 라우팅, 캐시, 배치 처리, 모니터링
    - LangChain의 Chains/Agents, Kubernetes, Airflow, FastAPI/Gradio로 구현

11. 모니터링·로그·피드백 루프
    - 응답 정확도, 지연(latency), 오류 유형, 사용성 수집해 지속 개선
    - 정확도/정확성, retrieval accuracy, grounded response rate, latency, cost 측정

12. 보안·프라이버시·거버넌스
    - 민감정보 식별·마스킹, 접근 제어, 감사 로그, 데이터 보존/삭제 규칙 적용
    - 내부 문서·개인정보 사용 시 암호화·로컬 호스팅된 벡터 DB 권장

<p>LangChain을 사용해 RAG 시스템을 구축할 때는 몇 가지 핵심 구성 요소들이 필요합니다. 각각의 구성 요소는 시스템 내에서 중요한 역할을 하며, 서로 유기적으로 연결되어 작동합니다.</p>
<p>첫 번째로 필요한 건 <strong>문서 로더(Document Loader)</strong> 입니다. 이는 외부에서 정보를 가져오는 역할을 합니다. 예를 들어 PDF, 웹페이지, 텍스트 파일, 데이터베이스 등 다양한 소스에서 문서를 읽어들여 시스템이 활용할 수 있는 형태로 변환합니다.</p>
<p>다음은 <strong>텍스트 분할기(Text Splitter)</strong> 입니다. 로딩된 문서가 너무 길면 검색 효율이 떨어지기 때문에, 문서를 일정 길이로 나누는 작업이 필요합니다. 이 과정을 통해 각 문서 조각이 임베딩과 검색에 적합한 형태가 됩니다.</p>
<p>그다음은 <strong>임베딩 모델(Embedding Model)</strong> 입니다. 문서 조각이나 사용자 질문을 숫자 벡터로 변환하는 역할을 하며, 이를 통해 문서 간 의미적 유사도를 계산할 수 있게 됩니다. OpenAI, Cohere, Hugging Face 모델 등 다양한 임베딩 옵션을 사용할 수 있습니다.</p>
<p>변환된 벡터는 <strong>벡터 데이터베이스(Vector Store)</strong> 에 저장됩니다. 이 데이터베이스는 나중에 사용자 질문이 들어왔을 때, 가장 관련 있는 문서들을 빠르게 검색하는 역할을 합니다. 대표적으로 FAISS, Pinecone, Weaviate 같은 솔루션이 많이 사용됩니다.</p>
<p>이제 검색된 문서 조각들을 바탕으로, <strong>프롬프트 템플릿(Prompt Template)</strong> 이 작동합니다. 사용자의 질문과 관련 문서를 조합해 생성 모델에 전달할 수 있는 입력 문장을 구성하는 단계입니다. 이 프롬프트가 얼마나 잘 구성되느냐에 따라 생성 결과의 품질이 달라질 수 있습니다.</p>
<p>마지막으로 LLM(Language Model), 즉 생성기 역할을 하는 모델이 사용자의 질문과 관련 문서를 기반으로 응답을 생성합니다. 이 과정을 <strong>Chain 또는 Agent</strong> 형태로 구성하여, 전체 RAG 파이프라인이 일관되게 작동하도록 만들 수 있습니다.</p>
<p>정리하면, LangChain을 활용한 RAG 시스템에서는 문서 로딩, 텍스트 분할, 임베딩, 벡터 저장소, 프롬프트 구성, LLM 응답 생성까지 일련의 흐름이 필요하고, 각각의 구성 요소가 자연스럽게 연결되어야 완성도 높은 응답을 생성할 수 있습니다.</p>
</details>

# 2. RAG 시스템의 성능을 평가하는 방법에는 어떤 것들이 있고, 독립 평가와 종단간 평가의 차이는 무엇인가요?

## RAG 성능 평가에서 자주 쓰이는 핵심 지표

1. **Retrieval 관련 지표**
   - Recall@k: 정답이 상위 k개 결과에 포함되는 비율
   - MRR(Mean Reciprocal Rank): 정답의 순위 역수를 평균한 값
   - Precision@k: 상위 k 결과 중 실제 유의미한 문서 비율
   - MAP(mean Average Precision): 검색 랭킹 전반의 정밀도

2. **Generation / Reader 관련 지표**
   - Exact Match / F1: 모델 추출 답변이 레퍼런스와 일치하는 비율
   - ROUGE / BLEU / METEOR: 요약·생성 품질의 유사성 지표
   - BLEURT / BERTScore: 의미적 유사성 지표(근거 일치성 보장 못함)

3. **Grounding·Fact / Hallucination 관련 지표**
   - Grounded Rate: 응답이 검색된 문서에 근거를 두고 있는 비율
   - Hallucination Rate: 응답에 출처 없는 주장·오류 포함 비율
   - Faithfulness metrics: 생성 응답이 근거 문서의 사실로부터 직접 추론 가능한지 검사
   - Attribution Accuracy: 인용한 출처가 실제 근거인지 검증한 비율

4. **사용자·운영 지표**
   - Helpfulness / Usefulness: 사용자 주관적 만족도 점수(5점 척도 등)
   - Time-to-Answer / Latency: 응답 지연 시간
   - Cost-per-query: API/연산 비용
   - Safe / Abstain Rate: "확실하지 않다" 응답 비율

## 독립 평가(모듈별) vs 종단간 평가(End-to-End) 차이와 장단점

| 항목 | 독립 평가 (모듈별) | 종단간 평가 (End-to-End) |
|------|------------------|----------------------|
| **정의** | RAG 파이프라인의 각 컴포넌트를 분리해 개별 성능을 측정 | 사용자 입력부터 최종 응답까지 전체 파이프라인을 통합해 평가 |
| **목적** | 문제 원인 진단과 모듈별 개선 효과 측정 | 실제 사용자 관점의 완성도·유용성·위험성 검증 |
| **장점** | 병목 식별이 용이하고 재현성 있는 실험 가능 | 모듈 간 상호작용을 반영하므로 실제 서비스 품질 정확히 반영 |
| **단점** | 모듈 간 누적 오류나 상호작용 효과를 반영하지 못할 수 있음 | 문제 발생 시 원인 분해가 어렵고 인적 비용(평가자) 많이 소요 |

<summary>실습해설</summary>

<p>RAG 시스템의 성능을 평가할 때는 검색(Retrieval)과 생성(Generation)이라는 두 가지 주요 단계에 대해 각각 또는 전체적으로 성능을 측정해야 합니다. 이때 평가 방식은 크게 독립 평가(모듈별 평가)와 종단간 평가(End-to-End 평가)로 나눌 수 있습니다.</p>
<p>먼저 독립 평가는 각 구성 요소의 성능을 분리해서 개별적으로 평가하는 방식입니다. 예를 들어 검색기의 성능은 주어진 질문에 대해 얼마나 관련 있는 문서를 찾아냈는지를 기준으로 평가하며, 대표적으로 Precision@k, Recall@k, MRR(Mean Reciprocal Rank) 같은 검색 기반 지표가 사용됩니다. 생성기 부분은 입력된 문서 기반으로 모델이 얼마나 자연스럽고 정확한 응답을 생성했는지, BLEU, ROUGE, METEOR, BERTScore 등의 자연어 생성 품질 지표로 측정할 수 있습니다.</p>
<p>반면 종단간 평가는 검색과 생성 과정을 통합해 전체 시스템이 사용자 질의에 대해 얼마나 잘 응답하는지를 측정하는 방식입니다. 여기서는 정답 일치율(Exact Match), 응답의 유용성, 사실성, 일관성 등을 평가하게 되며, 사람 평가(Human Evaluation)를 함께 병행하는 경우도 많습니다. 또한 최근에는 Faithfulness Score, Groundedness Score 같은 RAG 특화 평가 기준도 사용됩니다.</p>
<p>독립 평가는 시스템 내부의 병목이나 약점을 파악하는 데 유용하고, 종단간 평가는 사용자의 실제 경험에 더 가까운 평가 방식입니다. 두 방식은 서로 보완적이며, RAG 시스템을 고도화하기 위해서는 둘 다 적절히 활용하는 것이 중요합니다.</p>
</details>

# 3. RAG 시스템에서 'Agent'는 어떤 개념인지, 어떻게 구현할 수 있는지 구글 등에서 리서치하여 정리해보세요.

## RAG에서의 Agent란?

Agent는 "여러 기능을 주도적으로 조합·결정하는 소프트웨어 모듈"로서, 사용자 질의 처리 과정에서 검색, 문서 추출, 추가 도구 호출, 추론·생성, 후검증 등을 자동화하는 중재자(오케스트레이터) 역할을 합니다.

**역할 요약:**
- 어떤 도구(검색기·랭커·계산기·브라우저 등)를 언제 호출할지 결정
- 검색 결과를 어떻게 조합해 LLM 입력(프롬프트)을 구성할지 결정
- 생성 결과의 근거 정렬·후검증·출처 표기 담당
- 불확실할 때는 검토 요청, 사람 개입 또는 '확인 필요' 응답 선택

## Agent의 주요 구성요소

1. **Planner (또는 Policy)**
   - 쿼리 해석 → 단계(도구 호출 순서)를 계획
   - 예: "먼저 문서 검색 → 상위 5개 재정렬 → 요약 → 추가 검증"

2. **Executor (도구 실행기)**
   - 실제 도구 호출해 결과를 반환받음
   - 벡터 검색, BM25, 리랭커, LLM 생성기, 계산기, 외부 API 등

3. **Retriever / Vector Store**
   - 문서 인덱스에서 후보 청크를 찾아오는 기능

4. **Reranker / Filter**
   - 후보 청크를 정밀 평가해 LLM 입력용 상위 문단 선별

5. **Prompt Template / Context Assembler**
   - 검색 결과·메타데이터·시스템 지침을 결합해 최종 프롬프트 생성

6. **Generator / Reader (LLM)**
   - 최종 답변을 생성하거나 문서에서 직접 답 추출

7. **Verifier / Fact-checker**
   - 생성물의 사실성·근거 일치 여부를 자동·수동으로 검증

8. **Memory / Session State**
   - 대화 이력, 사용자 선호, 이전 검색 결과 등을 저장해 장기 문맥 제공

9. **Policy for Uncertainty & Safety**
   - "모르겠음/확인 필요" 응답 규칙, 민감 데이터 차단 규칙 정의

10. **Orchestration Layer / Retry & Caching**
    - 실패시 재시도, 결과 캐싱, 병렬 호출 관리, 비용 제어

### Agent 유형(설계 관점)

- **Rule-based Agent**: 명시적 규칙·워크플로로 도구 호출 순서 정의(단순·예측 가능, 확장성 낮음)
- **LLM-guided Planner**: LLM이 단계를 설계("생각해보고 단계 제안" 방식, 유연하지만 검증 필요)
- **Hybrid Agent**: 규칙 기반 + LLM 플래너 혼합
- **Agent with Tools**: 외부 도구 호출 가능하도록 인터페이스 제공(LangChain Agent 대표)

### LangChain 중심 구현 흐름

1. **Document Load & Indexing**
   - 문서 로더 → 텍스트 청킹 → 임베딩 생성 → VectorStore 인덱싱

2. **Retriever 래핑을 도구로 등록**
   - LangChain의 Tool 또는 retriever 래퍼로 정의

3. **Reranker/Reader 도구 등록**
   - Cross-encoder 기반 re-ranker, 요약기, 추출형 reader를 도구로 등록

4. **Planner 연결**
   - LangChain의 Agent/AgentExecutor 사용
   - 도구 목록 및 도구 설명을 등록
   - LLM이 도구 호출 의사를 표현하면 LangChain이 파싱하여 도구 실제 호출

5. **Prompt 설계**
   - 도구 출력 포맷(문서ID, 문단, 점수) 표준화
   - "출처 표기 방식", "불확실성 대처 규칙" 명시

6. **Verifier/Guardrails 추가**
   - 생성 후 자동 검증 체인(응답에 근거가 있는지 QA 체커로 재질문)

7. **실행·로깅·모니터링**
   - Agent의 도구 호출 로그, LLM 응답, 근거 출처를 전부 저장

### 구현 예시(개념적 코드 흐름, 의사 코드)

```
준비: retriever, reranker, LLM, tools 정의

Agent 구성(개념):
1. tools = [("search", retriever_tool), ("rerank", reranker_tool),
           ("summarize", summarizer_tool), ("calc", calculator_tool)]
2. agent = Agent(llm=LLM, tools=tools, planner="LLMPlanner" or "RulePlanner",
                prompt_template=template)
3. response = agent.run(user_query)

Agent 내부 흐름(예):
- plan = planner.plan(query)
- for step in plan:
    result = executor.call(step.tool, step.input)
    accumulate context
- if verify(context) fails:
    call verifier or ask human
- finalize answer with sources
```

### 실무적 설계·성능 최적화 팁

- 도구 설명(툴 메타데이터)을 신중히 작성(LLM 기반 플래너 의존)
- 단계별 토큰·비용 예산을 정함(토큰 초과·비용 폭등 방지)
- Reranker를 두 단계로 운용(벡터 검색 → cross-encoder 리랭킹)
- 프롬프트에 "출처 표기 규칙"과 "불확실성 대처 규칙" 엄격히 명시
- 도구 결과를 표준화된 JSON 형태로 반환하게 함
- 실패 정책(검색 결과 없음, 응답 검증 실패 시) 명확히 정의

### 안전·거버넌스·운영 고려사항

- **민감정보 필터링**: 문서 인덱싱 단계에서 개인정보·민감정보 식별·마스킹
- **검증 루프**: 법률·세무·의료 등 민감 도메인은 자동생성 즉시 배포하지 않고 검증자 승인 프로세스 구성
- **투명성**: 응답에 사용한 문서 ID, 문단 하이라이트, 근거 문장 등 함께 제공
- **비용·성능 모니터링**: LLM 호출 빈도, 평균 토큰 수, 검색 latency 모니터링해 SLA 관리
- **감사 로그**: Agent의 도구 호출 기록해 문제 발생 시 추적 가능하게 함

### 평가 기준(Agent 포함 RAG 관점)

- **Retrieval**: Recall@k, MRR(도구 호출 전/후 비교)
- **Agent 계획 적합성**: Planner가 생성한 단계가 작업에 맞는지(사람 평가)
- **End-to-End**: Grounded Rate, Hallucination Rate
- **운영지표**: Latency, Cost per query, Abstain Rate

<summary>실습해설</summary>

<p>RAG 시스템에서 ‘Agent’는 단순히 질문에 대한 검색과 답변 생성만 수행하는 고정된 흐름이 아니라, 질문을 이해하고 상황에 따라 필요한 행동을 스스로 결정하며 여러 단계를 유연하게 수행할 수 있는 실행 주체입니다.</p>
<p>예를 들어, 일반적인 RAG 시스템은 사용자의 질문을 받으면 관련 문서를 검색하고, 그 내용을 바탕으로 답변을 생성하는 정해진 구조를 따릅니다. 하지만 어떤 질문은 단순하지 않고, 질문을 쪼개거나, 여러 정보를 종합하거나, 추가적인 판단이 필요한 경우가 많습니다. 이럴 때 Agent는 질문의 목적을 이해하고, 어떤 도구를 언제 사용해야 할지 스스로 판단하며, 검색 → 요약 → 비교 → 응답 생성 같은 복합적인 과정을 순차적으로 수행할 수 있습니다.</p>
<p>Agent는 일종의 ‘지능형 문제 해결자’라고 보면 됩니다. LLM을 기반으로 하고, 다양한 도구와 상호작용하면서 복잡한 태스크를 해결하는 구조죠.</p>
<p>Agent를 구현하려면 다음과 같은 요소가 필요합니다.</p>
<p>첫째, 언어 모델(LLM)이 핵심입니다. Agent는 LLM을 기반으로 사용자의 질문을 분석하고 다음 행동을 결정합니다.</p>
<p>둘째, Tool 또는 Function이 필요합니다. 예를 들어 검색기, 계산기, 데이터베이스 조회기, 요약기 같은 기능이 대표적입니다. Agent는 이 도구들을 상황에 따라 호출해서 결과를 얻고, 다시 다음 행동으로 이어갑니다.</p>
<p>셋째, 메모리(Memory) 기능이 있다면 더 유용합니다. 이전 질문이나 중간 결과를 기억하고 활용할 수 있어 더 자연스럽고 일관성 있는 작업이 가능해집니다.</p>
<p>LangChain 같은 프레임워크에서는 Agent를 구현하는 기능을 기본적으로 지원합니다. initialize_agent 함수로 LLM과 사용할 도구들을 등록하고, 어떤 스타일의 Agent를 사용할지 정의하면 됩니다. 예를 들어, 검색기와 요약기를 도구로 등록해 두면, Agent가 사용자의 질문에 따라 먼저 검색을 하고, 그 결과를 요약한 뒤 최종 응답을 만드는 식으로 자동으로 동작하게 만들 수 있습니다.</p>
<p>정리하면, RAG 시스템에서 Agent는 단순한 검색-생성 구조를 넘어서 질문을 해석하고, 적절한 전략을 스스로 선택하며, 필요한 작업을 단계적으로 수행할 수 있는 유연한 실행 엔진이라고 할 수 있습니다. Agent가 들어가면 RAG 시스템은 훨씬 더 복잡한 질의에도 유연하게 대응할 수 있습니다.</p>
