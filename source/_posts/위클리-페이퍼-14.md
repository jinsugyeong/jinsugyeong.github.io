# 1. Docker 이미지와 컨테이너의 차이를 설명해보세요.

## 이미지(Image)

실행 가능한 애플리케이션의 정적 스냅샷(템플릿)입니다. 파일시스템, 애플리케이션 코드, 런타임, 라이브러리, 설정값 등이 계층(layer) 형태로 포함된 읽기 전용 아티팩트입니다.

<!-- more -->

## 컨테이너(Container)

이미지를 기반으로 실행되는 동적 인스턴스입니다. 이미지와 달리 쓰기 가능한 최상위 레이어를 가지며, 네트워크·프로세스·파일시스템이 호스트로부터 격리됩니다.



## 주요 차이점

| 항목 | 이미지 | 컨테이너 |
|------|--------|---------|
| 성격 | 정적(읽기 전용) 템플릿 | 동적 실행 단위(프로세스) |
| 변경 가능성 | 불변 | 실행 중 상태 변경 가능 |
| 생성 방법 | Dockerfile → docker build | docker run |
| 저장 위치 | 레지스트리 | 호스트 컨테이너 런타임 |

## 실무적 차이

- **불변성**: 이미지는 빌드 시점에 고정되어 배포·롤백이 용이합니다.
- **효율성**: 레이어 캐시로 빌드 효율이 높아지고 여러 컨테이너가 같은 레이어를 공유합니다.
- **디버깅**: 컨테이너는 `docker exec`로 내부 진입 가능하지만, 이미지는 재빌드 필요합니다.
- **배포**: CI에서 이미지 빌드 후 레지스트리에 푸시 → 운영에서 컨테이너 배포하는 흐름입니다.

<br>
<details>
<summary>실습해설</summary>
Docker 이미지란 컨테이너를 실행하기 위한 모든 요소가 포함된 정적인 템플릿입니다. 애플리케이션 코드, 라이브러리, 실행 환경, 의존성 등이 포함되어 있어, 어떤 환경에서도 동일하게 실행될 수 있도록 보장해줍니다.

<p>반면, 컨테이너는 이 이미지를 기반으로 실제로 실행된 인스턴스로, 격리된 공간에서 동작하는 일종의 경량 가상 환경입니다. 이미지는 변경되지 않는 반면, 컨테이너는 실행 중에 상태가 바뀔 수 있고, 메모리나 파일시스템에 변화가 발생할 수 있습니다.</p>
<p>즉, 이미지는 설계도이고, 컨테이너는 그 설계도를 바탕으로 실제로 동작하는 애플리케이션 인스턴스입니다.</p>
</details>

# 2. Docker Compose는 어떤 상황에서 유용하며, 일반 Dockerfile과 어떤 차이가 있나요?

## Dockerfile vs Docker Compose

| 항목 | Dockerfile | Docker Compose |
|------|-----------|-----------------|
| 목적 | 이미지 빌드 정의 | 컨테이너 실행 구성 |
| 사용 시점 | CI/빌드 단계 | 실행/오케스트레이션 |
| 구성 단위 | 단일 서비스 레이어 | 여러 서비스 YAML |
| 재사용성 | 이미지 버전 관리 | 서비스 조합 재현성 |

## Docker Compose가 유용한 상황

- "여러 서비스(웹 앱, DB, 캐시, 메시지 큐 등)를 동시에 띄워야 할 때"
- 서비스 간 네트워크·볼륨·환경변수를 일관되게 관리
- 로컬 통합 테스트 및 CI 파이프라인 구성

## 주요 명령어

```bash
docker compose up -d           # 백그라운드 실행
docker compose logs -f         # 실시간 로그
docker compose ps              # 서비스 상태 확인
docker compose down            # 스택 정리
docker compose up --scale web=3  # 수평 복제
```

## 한계

- 단일 호스트 중심으로 대규모 분산에 부적합
- 비밀 관리에 보안 고려 필요
- 프로덕션 운영에는 별도 오케스트레이터 필요

<br>
<details>
<summary>실습해설</summary>

<p>Dockerfile은 하나의 이미지를 어떻게 만들지를 정의하는 파일입니다. 예를 들어 Python 환경 위에 어떤 패키지를 설치하고, 어떤 코드를 복사할지를 단계별로 적어 놓은 것이죠.</p>
<p>반면 Docker Compose는 여러 개의 컨테이너를 한꺼번에 실행하고 관리하기 위한 도구입니다. 예를 들어 웹 서버, 데이터베이스, 캐시 서버를 동시에 띄워야 할 때, 각각의 설정을 하나의 YAML 파일에 정리해두고 docker compose up 한 줄로 전부 실행할 수 있습니다.</p>
<p>즉, Dockerfile은 '이미지 하나를 만드는 레시피'이고, Docker Compose는 '여러 서비스를 조합해서 실행하는 구성표'라고 이해하면 됩니다. 실무에서는 보통 Dockerfile로 각 서비스의 이미지를 만들고, Docker Compose로 그것들을 묶어서 실행하는 흐름으로 사용합니다.</p>
</details>

# 3. Kubernetes의 기본 개념은 무엇이며, Docker와는 어떤 관계가 있나요?

## Kubernetes 정의

"컨테이너화된 애플리케이션의 배포, 확장, 관리를 자동화하는 오케스트레이션 플랫폼"입니다.

## 핵심 구성 요소

- **Cluster/Node**: 여러 호스트가 모인 클러스터
- **Pod**: 최소 배포 단위 (하나 이상의 컨테이너)
- **Deployment/StatefulSet/DaemonSet**: 배포 정책 정의
- **Service**: Pod 접근을 위한 로드밸런싱 및 DNS
- **ConfigMap/Secret**: 설정 및 민감정보 관리
- **Volume/PersistentVolume**: 스토리지 관리
- **Control Plane**: 클러스터 전반 제어 (API Server, Scheduler 등)

## Docker와의 관계

- **역할**: Docker는 이미지 빌드, Kubernetes는 클러스터 수준 관리
- **런타임**: 현재 CRI 표준으로 containerd/CRI-O 연동
- **이미지**: "쿠버네티스는 Docker 이미지 형식을 사용"하여 호환성 유지

## Kubernetes의 이점

- 자동화된 수평 확장 및 부하 분산
- 장애 발생 시 자동 재시작·교체
- 롤링 업데이트/롤백으로 무중단 배포
- 서비스 디스커버리 및 설정 관리

## Docker Compose만으로 충분한 경우

- 단일 호스트 개발·테스트 환경
- 소규모 서비스로 고가용성 불필요

<br>
<details>
<summary>실습해설</summary>

<p>Kubernetes(쿠버네티스)는 컨테이너화된 애플리케이션을 대규모로 배포하고 관리하기 위한 오케스트레이션 플랫폼입니다. Docker가 컨테이너 하나를 만들고 실행하는 도구라면, Kubernetes는 수십~수백 개의 컨테이너를 여러 서버에 걸쳐 자동으로 배포하고, 장애가 나면 자동으로 복구하고, 트래픽이 늘면 자동으로 확장해주는 역할을 합니다.</p>
<p>핵심 개념으로는 Pod(컨테이너를 감싸는 최소 실행 단위), Deployment(Pod의 배포 방식 정의), Service(Pod에 접근하기 위한 네트워크 설정) 등이 있습니다.</p>
<p>Docker와의 관계를 정리하면, Docker는 '컨테이너를 만드는 도구'이고 Kubernetes는 '컨테이너들을 운영하는 도구'입니다. 소규모 환경에서는 Docker Compose로 충분하지만, 실제 프로덕션에서 고가용성과 자동 확장이 필요하다면 Kubernetes가 필요해집니다.</p>
</details>
