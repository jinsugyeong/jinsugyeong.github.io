1. Streamlit을 사용해서 AI 모델을 웹 애플리케이션에 통합하려면 모델 로드, 사용자 입력, 결과 출력의 단계를 거쳐야합니다. 각각의 단계에 대해 설명해주세요.

Streamlit을 사용해 AI 모델을 웹 애플리케이션에 통합할 때는
크게 모델 로드 → 사용자 입력 → 결과 출력 의 흐름으로 구성된다.
각 단계는 단순해 보이지만, 실제로는 역할이 명확하게 나뉘어 있다.

1.1 모델 로드 단계 (Model Loading)

AI 모델을 애플리케이션 시작 시점에 로드하며, “모델을 한 번만 로드하고 재사용”하는 것이 핵심입니다.

주요 작업:

  • 학습된 모델 파일(.pt, .onnx 등)을 메모리에 로드
  • 토크나이저, 전처리 객체 준비
  • Streamlit의 @st.cache 데코레이터로 중복 로드 방지

중요 포인트:

  • Streamlit은 스크립트가 재실행될 때마다 전체 코드를 다시 실행하므로, 캐싱이 필수
  • 모델 로드가 느린 경우(예: 대형 LLM), 캐시 없이는 매번 수십 초씩 대기

1.2 사용자 입력 단계 (User Input)

사용자가 웹 화면에서 데이터를 입력하는 단계입니다.

주요 작업:

  • 텍스트 입력, 파일 업로드, 슬라이더, 버튼 등의 UI 컴포넌트 활용
  • 입력값을 모델이 이해할 수 있는 형태로 전처리
  • 입력 변경 시 Streamlit 스크립트 재실행 관리

주의사항:

  • 사용자 입력이 바뀔 때마다 스크립트가 재실행되므로, 불필요한 연산은 조건문으로 제어
  • 파일 업로드 시 메모리 관리 필요

1.3 결과 출력 단계 (Result Output)

모델의 추론 결과를 사용자 친화적으로 표현합니다.

주요 작업:

  • 텍스트, 점수, 그래프, 이미지 등으로 출력
  • 중간 결과(확률, confidence) 함께 표시
  • 처리 시간이 긴 경우 로딩 메시지(spinner) 제공

UX 개선 팁:

  • 결과를 바로 보여주되, “왜 이런 결과가 나왔는지” 설명 추가
  • 모델의 불확실성(confidence score)도 함께 표시해 신뢰도 전달

실습해설

Streamlit으로 AI 모델을 웹에 통합할 때는 세 단계로 나눠서 생각하면 됩니다.

첫 번째는 모델 로드 단계입니다. 학습된 모델 파일을 메모리에 올리는 과정인데, Streamlit은 코드가 재실행될 때마다 전체를 다시 실행하기 때문에 @st.cache 같은 캐싱을 반드시 사용해야 합니다. 안 그러면 매번 모델을 새로 불러와서 엄청 느려집니다.

두 번째는 사용자 입력 단계입니다. 텍스트 입력, 파일 업로드, 슬라이더 같은 UI 컴포넌트로 데이터를 받고, 이걸 모델이 이해할 수 있는 형태로 전처리합니다.

세 번째는 결과 출력 단계입니다. 모델의 추론 결과를 텍스트, 그래프, 이미지 등으로 사용자에게 보여주는 과정입니다. 처리 시간이 길면 로딩 표시를 해주고, confidence score도 함께 보여주면 사용자 경험이 좋아집니다.

2. FastAPI로 AI 웹 API 서버를 만들 때 어떻게 구조를 나누면 좋을까요? 각 부분이 어떤 역할을 하는지 설명해주세요.

2.1 구조 분리 기준

FastAPI 기반 AI 서버는 다음과 같이 계층을 나눈다:

  • API 요청/응답 로직
  • 비즈니스 로직
  • 모델 로딩 및 추론 로직
  • 공통 설정 및 유틸

2.2 권장 디렉토리 구조

2.3 각 계층의 역할

main.py: 서버 진입점

  • FastAPI 앱 생성
  • 라우터 등록
  • 미들웨어 설정
  • 역할: 서버 시작과 전체 구성만 담당

api/: API 레이어

  • 외부 요청 수신
  • Request/Response 연결
  • HTTP 레벨 처리 (헤더, 상태 코드 등)
  • 역할: HTTP 통신 담당, 실제 로직은 services로 위임

schemas/: 데이터 검증

  • Pydantic 모델로 입력/출력 명확화
  • 타입 안정성 확보
  • API 문서 자동 생성
  • 역할: 데이터 구조 정의 및 검증

models/: 모델 로딩 & 추론

  • 모델 로딩 함수
  • 추론 함수 정의
  • 프레임워크 의존성 포함 (PyTorch, ONNX 등)
  • 역할: 순수 모델 연산만 담당

services/: 비즈니스 로직

  • 입력 전처리
  • 모델 호출
  • 결과 후처리
  • 예외 처리
  • 역할: API와 모델 사이의 중재자

core/utils/: 공통 기능

  • 설정값, 환경 변수 관리
  • 로깅 설정
  • 공통 함수 (파일 I/O, 유틸 등)
  • 역할: 전역적으로 쓰이는 기능 제공

실습해설

FastAPI로 AI 서버를 만들 때는 역할별로 코드를 분리하는 것이 핵심입니다.

api/ 폴더에는 HTTP 요청을 받고 응답을 보내는 엔드포인트 코드만 넣고, 실제 AI 추론 로직은 models/ 폴더에 분리합니다. schemas/ 폴더에는 Pydantic으로 입력/출력 데이터 구조를 정의하고, services/ 폴더에는 전처리, 모델 호출, 후처리를 연결하는 비즈니스 로직을 넣습니다.

이렇게 계층을 나누면 모델을 교체하거나 API를 수정할 때 다른 부분에 영향을 주지 않고 독립적으로 작업할 수 있습니다. API 레이어는 HTTP 통신만, 모델 레이어는 순수 추론만, 서비스 레이어는 그 사이를 중재하는 역할만 담당하도록 설계하는 것이 좋습니다.

3. Notion AI 같은 서비스가 어떤 구조로 되어있을지 상상해서 정리해보세요. (예: Streamlit + FastAPI + 최적화된 LLM)

3.1 서비스 개요

Notion AI는 문서 요약, 문장 재작성, 핵심 포인트 정리 등을 제공하는 AI 서비스입니다.

3.2 아키텍처 흐름

3.3 Frontend (Streamlit UI Layer)

역할:

  • 사용자가 문서를 입력하거나 업로드
  • 요약 옵션 선택 (짧게 / 자세히 등)
  • 결과를 시각적으로 표시

주의:

  • 모든 요청은 FastAPI로 전달 (직접 모델 호출 없음)
  • UI는 “보여주기만” 하고, 실제 AI 처리는 백엔드가 담당

3.4 Backend (FastAPI API Gateway)

API 엔드포인트 예시:

  • POST /api/v1/summarize → 요약 요청
  • GET /api/v1/status/{job_id} → 작업 상태 조회
  • GET /api/v1/health → 서버 상태 확인

역할:

  • 요청 검증 및 인증
  • 비동기 처리(async)로 동시 사용자 요청 대응
  • Inference Service로 작업 전달
  • 결과 캐싱 (동일 요청 재사용)

3.5 Inference Service (추론 최적화)

모델 최적화 흐름:

  • 학습: PyTorch 기반 LLM
  • 변환: ONNX 포맷으로 변환
  • 배포: TensorRT로 FP16/INT8 최적화
  • 서버 시작 시 한 번만 로드

최적화 효과:

  • PyTorch 원본 대비 2~10배 빠른 추론 속도
  • GPU 메모리 사용량 감소
  • 동시 사용자 처리 능력 향상

3.6 멀티유저 요청 처리

처리 구조:

  • Task Queue 활용 (Redis, RabbitMQ 등)
  • 긴 작업은 비동기로 처리
  • 즉시 job_id 반환
  • 클라이언트가 결과 조회

3.7 보안 요소

CORS (Cross-Origin Resource Sharing):

  • 허용된 도메인만 API 접근 가능
  • 프론트엔드와 백엔드가 분리된 경우 필수

인증 (Authentication):

  • JWT 기반 사용자 인증
  • API 키 발급 및 Rate Limiting (과도한 요청 방지)

네트워크:

  • HTTPS 통신 강제
  • 추론 서버는 Private Network에 배치 (외부 직접 접근 차단)

3.8 Docker 기반 배포

3.9 클라우드 배포 (AWS 기준)

  • EC2 (GPU): 추론 서버 (g4dn.xlarge 등)
  • EC2 (CPU): FastAPI 서버
  • ALB (Application Load Balancer): 트래픽 분산
  • S3: 사용자 업로드 문서 저장
  • ECR: Docker 이미지 관리

3.10 모니터링 및 로깅

모니터링:

  • API 응답 시간 (Latency)
  • 추론 속도 (Inference Time)
  • GPU 사용률

로깅:

  • 요청/응답 로그 (API 호출 추적)
  • 추론 에러 로그 (모델 실패 케이스)
  • 사용자 요청 추적 로그 (어떤 기능이 많이 쓰이는지 분석)

핵심 요약

Streamlit 기반 AI 웹은 **”단계 흐름이 명확할수록 안정적”**이며, FastAPI 서버는 역할 분리를 통해 유지보수성을 확보합니다. ONNX/TensorRT 최적화와 비동기 처리 구조가 대규모 AI 서비스의 기본입니다.


실습해설

Notion AI 같은 서비스의 구조를 상상해보면, 크게 세 개의 계층으로 나눌 수 있습니다.

프론트엔드(Streamlit)는 사용자가 문서를 입력하고 옵션을 선택하고 결과를 보는 UI 역할만 합니다. 직접 모델을 호출하지 않고, 모든 요청을 백엔드로 전달합니다.

백엔드(FastAPI)는 API 게이트웨이 역할로, 요청 검증, 인증, 비동기 처리를 담당합니다. 긴 작업은 Task Queue(Redis 등)에 넣고 job_id를 반환해서 클라이언트가 나중에 결과를 조회하는 방식으로 처리합니다.

추론 서버는 ONNX/TensorRT로 최적화된 LLM을 GPU 위에서 실행하며, 순수하게 추론만 담당합니다. 이렇게 UI, API, 추론을 완전히 분리하고 Docker Compose로 배포하면, 각 컴포넌트를 독립적으로 확장하고 관리할 수 있는 구조가 됩니다.
