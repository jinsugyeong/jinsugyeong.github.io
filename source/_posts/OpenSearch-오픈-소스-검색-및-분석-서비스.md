## OpenSearch를 공부하게 된 이유

사실 처음엔 OpenSearch가 검색 엔진인지도 몰랐다. 그냥 "AI/ML 쪽에서 많이 쓰인다더라" 하는 키워드만 알고 언젠가 배워야지 하고 있었다.

그러다 독서 기록을 관리하고 내가 읽은 책을 기반으로 AI가 책을 추천해주는 서비스를 개인 프로젝트로 기획하게 됐는데 부트캠프 때 했던 RAG 프로젝트들이 떠올랐다. 당시에 검색 품질 때문에 고생했던 기억이 있어서 해당 문제를 어떻게 해결해야할까 고민하던 중 OpenSearch를 생각하게 되었고 그렇게 OpenSearch에 대해 공부하게 되었다.



# OpenSearch란?

원래 Elasticsearch라는 검색 엔진이 있었는데 2021년에 무료였던 라이선스를 유료로 바꿔버려서 이걸 포크해서 완전 오픈소스로 만든게 OpenSearch이다.

간단하게 말하면 검색에 특화된 데이터베이스다. 

제목도 그렇게 계속 검색 엔진이라고 하다가 뜬금없이 왜 데이터베이스라고 하냐면 **데이터를 JSON 형태로 저장하고 텍스트 검색, 필터링, 랭킹, 집계를 매우 빠르게 수행** 하기 때문이다.

그럼 여기서 의문이 든다. 그럼 OpenSearch만 쓰면 되는거 아니야? 벡터임베딩 문제라면 똑같이 지원되는 PostgrSQL 쓰면 되는거아니야?

## DB(PostgreSQL)가 있는데 OpenSearch를 쓰는 이유

| 항목 | **PostgresSQL** | **OpenSearch** |
| --- | :---: | :---: |
| **역할 분담** | 원본 데이터 기록(내역, 정보, 관계 중심) | 대량 데이터에서 빠른 탐색(전문 검색, 로그 분석, 정행/비정형 데이터) |
| **기술적 차이** | 정방향 인덱스(B-tree) 구조 → `LIKE '%검색%'`은 인덱스를 못 써서 데이터 증가 시 Full Scan 발생 | 역색인(Inverted Index) 구조 → 필요한 문서만 접근하여 대용량에서도 빠른 검색 |
| **정합성 & 아키텍처** | **Source of Truth**<br>트랜잭션·정합성 보장 (쓰기 기준 저장소) | **Read Model**<br>검색 성능 최적화용 복제본 → 비동기 동기화 |

OpenSearch만으로는 정합성과 트랜잭션이 부족하고, PostgreSQL만으로는 대규모 검색과 랭킹이 한계가 있다.

그래서 보통은 둘을 같이 쓴다. PostgreSQL에 원본 데이터를 저장하고, OpenSearch에는 검색용으로 필요한 데이터만 따로 넣어두는 식이다.

# 핵심 개념들

## 내부구조

{% asset_img image.png alt text %}

### 도큐먼트 (Document)

OpenSearch 데이터의 최소 단위. JSON 포맷으로 되어 있으며, 일반적인 데이터베이스의 한 행(row)이라고 생각하면 된다.

```json 
{
  "title": "채식주의자",
  "author": "한강",
  "genre": "소설",
  "description": "폭력성과 욕망에 저항하는 한 여자의 이야기"
}
```
이런 JSON 하나가 도큐먼트 하나다.

### 인덱스(Index)

도큐먼트들이 모인 논리적인 집합. 데이터베이스의 테이블과 같은 개념으로, 데이터를 저장하기 위해 가장 먼저 생성해야 하는 단위이다.


### 샤드 (Shard)
인덱스를 여러 개로 쪼개어 물리적으로 저장하는 분할 단위. 여러 노드(서버)에 데이터를 분산시켜 병렬 검색을 가능하게 하며, 데이터의 안정성을 위한 복제본(Replica)을 가질 수 있다.

### 세그먼트 (Segment)
샤드 내부에서 데이터를 실제로 관리하는 물리적 저장 단위. 인덱싱된 도큐먼트들은 '리프레시' 과정을 거쳐 세그먼트 형태로 생성되어야만 비로소 검색이 가능한 상태가 된다.





## 역색인(Inverted Index) 
OpenSearch가 검색이 빠른 이유가 바로 이것 때문이다.

일반적인 DB는 데이터를 찾을 때 "이 행에 이 단어가 있나?" 하고 처음부터 끝까지 훑는다. 반면 OpenSearch는 데이터를 저장할 때부터 **"이 단어가 어떤 문서에 있다"는 지도**를 미리 만들어둔다.

```
"채식주의자" → [문서1]
"한강"       → [문서1, 문서7, 문서23]
"소설"       → [문서1, 문서3, 문서5 ...] 
```

"한강"을 검색하면 전체를 뒤지는 게 아니라 이 지도에서 바로 찾아간다. 그래서 빠르다.


## 형태소 분석기(Analyzer) - 한국어 검색의 핵심
영어는 공백으로 단어를 나누면 되는데, 한국어는 "채식주의자"를 어떻게 쪼개느냐가 검색 품질을 결정한다.
OpenSearch에서 한국어 검색을 제대로 하려면 Nori 분석기를 써야 한다. Nori는 한국어 형태소 분석기로, "채식주의자"를 "채식 + 주의 + 자" 이런 식으로 의미 있는 단위로 쪼개준다.
덕분에 "채식"만 검색해도 "채식주의자"가 결과에 나오게 된다. 이게 없으면 한국어 검색이 굉장히 허술해진다.

## 매핑(Mapping)
DB의 스키마와 비슷한 개념이다. 각 필드를 어떤 타입으로 저장할지 미리 정의해두는 것인데, 검색 품질에 직접 영향을 준다.
예를 들어 책 제목은 형태소 분석을 해서 부분 검색이 되게 하고, 출판년도는 숫자로 저장해서 범위 검색이 되게 하는 식이다.

```json
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "nori"
      },
      "published_year": {
        "type": "integer"
      }
    }
  }
}
```


# 동작 방식
## 인덱싱 흐름 (Indexing Flow)

검색을 이해하기 전에, 데이터가 OpenSearch에 어떻게 저장되고 검색 가능한 상태가 되는지를 먼저 알아야 한다.

문서를 저장하는 요청을 보내면 OpenSearch는 다음 순서로 처리한다.

{% asset_img image-1.png alt text %}

```
1. 문서 수신
   POST /books/_doc
   { "title": "채식주의자", "author": "한강", ... }

2. 분석기(Analyzer) 처리
   텍스트 필드를 토큰으로 분해
   "채식주의자" → ["채식", "주의", "자"]

3. 역색인 업데이트 + 메모리 버퍼에 적재
   아직 디스크에 쓰지 않음 → 검색 불가

4. 리프레시 (Refresh) — 기본 1초마다
   메모리 버퍼 → 세그먼트(Segment) 생성
   이 시점부터 검색 가능

5. 플러시 (Flush)
   세그먼트를 디스크에 영구 저장 (fsync)
   트랜잭션 로그(Translog) 비움
```

핵심은 **저장 요청과 검색 가능 사이에 최대 1초의 딜레이가 있다**는 것이다. 이걸 near real-time(NRT) 검색이라고 부른다.

### 세그먼트 병합 (Merge)

문서를 계속 저장하다 보면 작은 세그먼트가 쌓인다. 세그먼트가 너무 많으면 검색 시 모든 세그먼트를 다 확인해야 해서 느려진다.

OpenSearch는 백그라운드에서 작은 세그먼트들을 주기적으로 합쳐 큰 세그먼트로 병합한다. 이 과정에서 삭제된 문서도 실제로 디스크에서 제거된다. (OpenSearch는 문서 삭제 요청이 들어오면 즉시 지우지 않고 "삭제 표시"만 해두고, 병합 때 실제 제거한다.)

```
세그먼트1 [문서1, 문서2, 문서3(삭제됨)]
세그먼트2 [문서4, 문서5]
세그먼트3 [문서6]
        ↓ 병합
세그먼트A [문서1, 문서2, 문서4, 문서5, 문서6]  ← 삭제 문서 실제 제거
```

## 키워드 검색(Lexical Search)

키워드 검색은 우리가 흔히 아는 "이 단어가 문서에 있는가"를 기준으로 검색하는 방식이다. 앞서 설명한 역색인을 그대로 활용한다.

검색어를 입력하면 분석기(Analyzer)가 먼저 텍스트를 토큰으로 쪼갠 뒤, 역색인에서 해당 토큰이 포함된 문서를 찾아온다.

```
검색어: "한강 소설"
         ↓ Nori 분석기
토큰화: ["한강", "소설"]
         ↓ 역색인 조회
결과: "한강"이 있는 문서 ∩ "소설"이 있는 문서
```

### BM25 — 어떤 문서가 더 관련 있는가

문서를 찾는 건 그냥 역색인만 있으면 되는데, 문제는 "여러 개가 나왔을 때 어떤 순서로 보여줄 것이냐"다.

OpenSearch는 **BM25(Best Match 25)** 알고리즘으로 각 문서에 점수를 매겨 랭킹을 정한다. TF-IDF를 개선한 알고리즘인데, 핵심 아이디어는 두 가지다.

- **TF (Term Frequency)**: 문서 안에서 검색어가 많이 나올수록 관련도가 높다. 단, 너무 많이 나온다고 무한정 점수가 오르진 않는다 (수렴 처리).
- **IDF (Inverse Document Frequency)**: 모든 문서에 흔하게 나오는 단어는("이", "그", "을") 점수를 낮게 준다. 희귀한 단어일수록 해당 문서의 특징을 잘 나타낸다고 보는 것.

```
BM25 점수 ∝ 검색어가 이 문서에 얼마나 많이 나왔나
           × 전체 문서 중 이 단어가 얼마나 희귀한가
           × 문서 길이 보정 (짧은 문서에 불이익 방지)
```

### 키워드 검색의 한계

BM25는 단어가 일치해야 점수가 나온다. "우울한 직장인이 공감할 소설"로 검색하면 "우울", "직장인", "공감", "소설" 이 단어들이 실제로 들어간 문서만 찾는다.

"감정 소진된 현대인의 이야기" 같은 문서는 의미는 비슷해도 단어가 다르니 0점이다. 이게 키워드 검색의 근본적인 한계다.


## 벡터 검색(Semantic Search)

키워드 검색이 "단어 일치"라면, 벡터 검색은 "의미 유사도"로 찾는 방식이다.

### 텍스트를 숫자 벡터로

핵심은 텍스트를 임베딩(Embedding) 모델로 고차원 숫자 배열(벡터)로 변환하는 것이다.

```python
# "채식주의자" → OpenAI text-embedding-3-small 기준 1536차원 벡터
[0.023, -0.451, 0.117, 0.382, ..., -0.091]  # 1536개의 숫자
```

의미가 비슷한 텍스트는 벡터 공간에서 가까운 위치에 놓인다. "채식주의자"와 "폭력에 저항하는 여자의 이야기"는 단어가 달라도 벡터 거리가 가깝다.

### KNN — 가장 가까운 벡터 찾기

검색할 때는 쿼리 텍스트도 벡터로 변환한 뒤, 저장된 벡터들과의 거리를 측정해 가장 유사한 문서를 반환한다.

```
"우울한 직장인이 공감할 소설" → [0.11, -0.34, ...] 쿼리 벡터
                                      ↓
              저장된 모든 책 벡터와 거리 계산 (코사인 유사도)
                                      ↓
                          유사도 높은 순서로 반환
```

거리 계산 방식은 여러 가지인데, 텍스트 검색에서는 **코사인 유사도**를 주로 쓴다. 벡터의 크기보다 방향이 얼마나 비슷한지를 보는 것인데, 텍스트 길이에 상관없이 의미의 방향성을 비교할 수 있어서 적합하다.

### HNSW — 빠른 근사 검색

문제는 저장된 벡터가 수백만 개라면 전부 비교하는 건 너무 느리다는 것이다.

OpenSearch는 **HNSW(Hierarchical Navigable Small World)** 알고리즘을 써서 정확한 최근접 이웃이 아닌 **근사 최근접 이웃(ANN)** 을 빠르게 찾는다. 여러 계층의 그래프 구조로 미리 연결해두고, 멀리서부터 점점 좁혀 들어오는 식이라 전체를 비교하지 않아도 된다.

```json
"knn_vector": {
  "type": "knn_vector",
  "dimension": 1536,
  "method": {
    "name": "hnsw",
    "space_type": "cosinesimil",
    "engine": "nmslib"
  }
}
```

### 벡터 검색의 한계

반대로 "한강 소설"처럼 정확한 고유명사나 특정 단어를 찾는 경우엔 키워드 검색보다 오히려 부정확할 수 있다. 의미적으로 비슷하지만 엉뚱한 결과가 나오기도 한다. 결국 둘 다 약점이 있다.


## 하이브리드 검색 (Hybrid Search)

그래서 실전에서는 키워드 검색과 벡터 검색을 합친 **하이브리드 검색**을 많이 쓴다.

BM25는 정확한 단어 매칭에 강하고, KNN은 의미 기반 유사도에 강하니 둘의 결과를 합쳐서 최종 랭킹을 내는 것이다.

```
"한강의 채식주의자 같은 분위기 소설"
         ↓
BM25 검색:  "한강", "채식주의자" 단어 포함 문서에 높은 점수
KNN 검색:   "폭력·저항·내면세계" 의미 가진 문서에 높은 점수
         ↓
두 점수를 정규화 후 가중 합산
         ↓
최종 결과: 단어도 맞고, 의미도 비슷한 문서가 상위 랭크
```

### 점수 합산 방법 — 정규화가 필요한 이유

BM25 점수와 KNN 유사도 점수는 스케일이 다르다. BM25는 0~수십, KNN 코사인 유사도는 0~1. 그냥 더하면 BM25가 압도적으로 커져서 키워드 검색이나 다름없어진다.

그래서 OpenSearch는 **Min-Max 정규화**로 각 점수를 0~1 범위로 맞춘 뒤 합산한다.

```
정규화 점수 = (점수 - 최솟값) / (최댓값 - 최솟값)

최종 점수 = (BM25 정규화 점수 × 키워드 가중치)
           + (KNN 정규화 점수 × 벡터 가중치)
```

OpenSearch에서는 이 파이프라인을 **Search Pipeline**으로 설정해서 쓴다.

```json
{
  "description": "하이브리드 검색 파이프라인",
  "phase_results_processors": [
    {
      "normalization-processor": {
        "normalization": { "technique": "min_max" },
        "combination": {
          "technique": "arithmetic_mean",
          "parameters": { "weights": [0.3, 0.7] }
        }
      }
    }
  ]
}
```

`weights`의 `[0.3, 0.7]`은 BM25 30%, KNN 70% 비율이다. 어떤 검색이 더 중요한지에 따라 조절하면 된다. 내 프로젝트에서는 의미 기반 추천이 핵심이라 KNN 가중치를 높게 설정했다.

```jsonc
// 실제 하이브리드 검색 쿼리
{
  "query": {
    "hybrid": {
      "queries": [
        {
          "match": {
            "description": { "query": "우울한 현대인 이야기" }  // BM25
          }
        },
        {
          "knn": {
            "embedding": {
              "vector": [0.11, -0.34, ...],  // 쿼리 임베딩 벡터
              "k": 10
            }
          }
        }
      ]
    }
  }
}
```

## OpenSearch와 RAG

글 첫머리에서 부트캠프 때 RAG 프로젝트를 했는데 검색 품질 때문에 고생했다고 했다. 이 부분을 이제 회수할 시간이다.

### RAG란

RAG(Retrieval-Augmented Generation)는 LLM이 답변을 생성할 때 외부 데이터를 먼저 검색해서 참고하게 하는 패턴이다.

LLM은 학습 데이터 바깥의 정보(최신 뉴스, 사내 문서, 개인 데이터)를 모른다. 그래서 "먼저 관련 문서를 검색해서 → LLM에게 같이 넘겨주는" 방식으로 이 한계를 보완한다.

```
사용자 질문
    ↓
검색기(Retriever): 질문과 관련된 문서를 DB에서 찾아옴
    ↓
LLM: "너의 질문 + 찾아온 문서를 참고해서 답변해줘"
    ↓
답변 생성
```

### RAG에서 OpenSearch가 하는 역할

RAG의 핵심은 **얼마나 관련성 높은 문서를 찾아오느냐**다. 검색기가 엉뚱한 문서를 가져오면 LLM이 아무리 좋아도 답변 품질이 떨어진다. 부트캠프 때 고생했던 것도 바로 이 부분이었다.

당시에 단순 벡터 검색만 썼는데, 예를 들어 "이 책의 저자가 누구야?" 같은 구체적인 질문에 벡터 검색이 의미 유사도로만 찾다 보니 엉뚱한 책이 섞여 들어왔다. 반대로 "고독하고 우울한 소설 추천해줘" 같은 감성적 질문엔 키워드 검색이 전혀 못 찾았다.

OpenSearch의 하이브리드 검색이 이 두 문제를 동시에 해결한다.

```
"고독하고 우울한 소설 추천해줘"
        ↓ 하이브리드 검색
BM25: "고독", "우울", "소설" 단어 포함 문서 스코어링
KNN:  "감정적 고립, 내면 탐구" 의미와 유사한 문서 스코어링
        ↓ 정규화 후 합산
관련성 높은 책 목록 (컨텍스트)
        ↓
LLM: "이 책들을 참고해서 추천 이유를 한국어로 설명해줘"
        ↓
"채식주의자는 현대 사회의 폭력성에 저항하는 내면의 고독을 ..."
```

내 프로젝트에서는 사용자가 읽은 책들의 임베딩 벡터를 평점 가중치로 합산해서 "이 사람의 취향 벡터"를 만들고, 그 벡터로 OpenSearch KNN 검색을 해서 비슷한 책들을 찾아온다. 그 결과를 GPT-5-nano에게 넘겨서 추천 이유를 생성한다.

키워드 검색만 했다면 "내가 좋아하는 분위기의 책"을 찾는 건 불가능했을 것이다. 결국 처음에 품었던 "추천 시스템인데 왜 키워드 검색만 하고 있지?"라는 위화감의 답이 여기에 있다.
